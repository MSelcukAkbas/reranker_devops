# Coverage view vs note view (2026-09-30, searchslim 0.4.0)

Offline benchmark (`benchmark/bench.py run --view notes|coverage --model-cmd "python3 -m searchslim bench-model"`),
27 tasks, chars/4 tokens, trigger = budget. The coverage view leads with an index of every
matching file and fills the rest of the budget with evidence; the note view ends with a
"not shown" count.

| budget | view | mode | tokens | kept | recoverable | lost |
|---|---|---|---|---|---|---|
| 2000 | notes | rules | 30497 | 32/36 | 4 | 0 |
| 2000 | coverage | rules | 30411 | 32/36 | 4 | 0 |
| 2000 | notes | rules+model | 32207 | 36/36 | 0 | 0 |
| 2000 | coverage | rules+model | 32254 | 36/36 | 0 | 0 |
| 800 | notes | rules | 14024 | 16/36 | 18 | 2 |
| 800 | coverage | rules | 14558 | 17/36 | 17 | 2 |
| 800 | notes | rules+model | 14507 | 32/36 | 2 | 2 |
| 800 | coverage | rules+model | 14848 | 31/36 | 3 | 2 |

Raw total: 76565 tokens.

- At the default budget (2000) the index costs no evidence: same critical lines kept, same tokens.
- At 800 the index takes room from evidence: rules+model keeps one critical line fewer
  (pytest-raises-impl). The 2 lost lines are the count-mode task (pytest-test-counts),
  which the coverage view does not touch.
- "recoverable" / "extra searches" here are an offline upper bound (every recoverable file
  counts as one more search). Whether the agent actually stops re-searching when it sees a
  complete index is a behavioral question for the live run (arvis_code, 2000 trigger, hook on/off).
