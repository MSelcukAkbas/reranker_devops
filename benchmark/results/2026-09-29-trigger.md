# Trigger threshold (2026-09-29)

`python3 benchmark/bench.py run --tokenizer chars --repeat 1 --trigger-tokens T --model-cmd "python3 -m searchslim bench-model"`,
budget 2000 tokens, same 27-task fixture set as `2026-09-29-tasks27.md`.

| trigger | mode | tokens | vs raw | kept | recoverable | lost | extra searches |
|---|---|---|---|---|---|---|---|
| 0 (= budget) | rules | 30592 | 40% | 32/36 | 4 | 0 | 3 |
| 0 (= budget) | rules+model | 32538 | 42% | 36/36 | 0 | 0 | 0 |
| 6000 | rules | 48772 | 64% | 36/36 | 0 | 0 | 0 |
| 6000 | rules+model | 49099 | 64% | 36/36 | 0 | 0 | 0 |

Why 6000: a live Windows run (arvis_code, 0.3.1) trimmed a ~4.3k-token Grep result to ~2k;
the agent then ran 3 extra Greps for what was cut (2 -> 5 turns, $0.247 -> $0.289).
With a 6000 trigger only really large outputs are cut; mid-sized ones (where rules lost
evidence here) pass whole, so no critical line is lost in either mode and no extra search
is needed. The hook and CLI default to 6000 (`SEARCHSLIM_TRIGGER_TOKENS`); the benchmark
keeps 0 by default so earlier tables stay comparable.
